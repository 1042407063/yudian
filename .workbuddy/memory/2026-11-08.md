# 2026-11-08

## 适配罗技 G913 TKL 键盘电量（已真机验证）

- 现象：面板读不到键盘电量，显示「未提供电量接口」。
- 硬件：`046D:C547` LIGHTSPEED 接收器，HID 集合 `FF00/0001`(7B) 与 `FF00/0002`(20B)，
  真正应答的只有**长报文集合的 1 号通道**（HID++ 4.2）。产品名对所有集合都是 "USB Receiver"。
- 根因：G913 TKL **没有 `0x1000` 百分比特性**，只暴露 `0x1001` 电压。
  `func0` 回帧 `11 01 07 0s 0F 6C 00` = 大端 3948 mV + 充电标志。
  旧 `HppLink::Battery()` 按小端解析成 27663 mV，被范围检查丢掉 → 整台设备判为不支持。
- 修复：
  - `decode.h` 新增纯函数 `DecodeLogitechVoltage()`（大端优先、小端兜底、3000–5000 mV 合理性）与
    `LogitechVoltageToPercent()`（Linux 内核 `hidpp20_map_battery_capacity()` 的 100 点曲线）。
  - `HppLink::Battery()` 增加 `estimated` 出参；解析 flags（bit7 外接电源 / bit0–2 充电状态）；
    无 `0x1000` 时用电压曲线估百分比。
  - `Reading::approximate`：面板 `≈73%` + 「电压估算」，托盘/--list 同步；`MergeReading` 沿用旧值时保留该标记。
  - 设备名在 " LIGHTSPEED" 处截断，避免 58 字符全名被省略号吃掉。
- 技术依据：openlogi 0x1001 文档（大端 mV + flags）、Linux `hid-logitech-hidpp.c` 电压曲线、
  Solaar / kernel 邮件列表里 G915 特性表（确认只有 0x1001）。
- 新增探针 `dev/probes/logitech_g913.py`（只读，ctypes 走 HID++，用于复现与回归）。
- 验证：`build.bat` 通过，自检 38 条全过；`yudian.exe --list` 实测
  `G913 TKL | 键盘 | ≈73% | 3948 mV | 放电中 | logitech`，报告里 `电压估算=1 any=1`。
- 注意：估算值与 G HUB 可能差几个百分点，低电量段误差更大；这是硬件只给电压导致的，不是 bug。

## 追加：充电跳变 / 绿色图标 / 双模去重（同日 21:20 后）

- 用户反馈三点：插线瞬间电量 +20%、充电中图标要变绿、鼠标插数据线出现两个一样的鼠标。
- 关键实测：G913 TKL 插线后**换 USB 身份**——无线接收器 `046D:C547` → 有线直连 `046D:C343`
  （C547 的 1 号通道随即报错误码 0x08）。电压 3948 mV/flags 0x00 → 4133 mV/flags 0x80
  → 4174 mV。充电端电压 = OCV + I·R，比开路电压高约 185 mV；套放电曲线 73%→97%。
- 官方机制（回答用户提问）：G913 这代**没有精确电量**，只有 0x1001 电压；G HUB 用每个型号
  内置的 **PowerModel**（LGS 时代 XML 电压→容量表，G HUB 内嵌），区分充放电、充满时校准到
  最大电压。罗技官方支持文档承认 G HUB 百分比是估算，受充电电压/老化/温度影响，还有
  G303「充电涨得快、拔线掉得快」的已知问题说明。新一代用 0x1004 unifiedBattery 才给 SoC。
- 修复：
  - `decode.h` 新增 `LogitechBatteryPercent(mv, charging, full)`（充电扣 185 mV IR + 满电校准）
    与 `SmoothEstimatedLevel(prev, next, elapsed)`（每轮 ±6 点，离线 >30 分钟直接采用）。
  - `HppLink::Battery()` 先解 flags 再算百分比；`ScanLogitech` 按 `0x0005` 型号名归一化 key，
    transport 改「USB 有线」，估算值按身份做速率限制（新增 `g_logiLevelState`）。
  - `ui.cpp`：充电中数字 + 电池胶囊用 `g_colors.ok` 绿色，优先于低电量红/橙；托盘 logo 不动。
  - `app.h` 新增 `MergeWiredWirelessDuplicates()`，`MonitorScan` 在所有链路后合并
    「同名 + 同品类 + 同 provider + 一条有线一条无线」，保留充电中那条，汇总统计在合并后重算。
- 验证：`build.bat` 通过、自检 **53/53**；真机插线 `--list` =
  `G913 TKL | 键盘 | ≈80% | USB 有线 | 充电中`（4174 mV 扣 IR 后 3989 mV）；
  `--shot` 截图确认绿色胶囊 + 绿色 ≈80%。双模去重由 3 条自检用例覆盖（真机当时未插鼠标线）。
- 坑：编译时 `yudian.exe` 被用户正在运行的实例占用 → `Permission denied`，结束后才链接成功。
  以后重编前先查 `Get-Process yudian`。

## 追加：拔线跳 99%、证伪自报电量、追平 G HUB（22:00 后）

- 用户反馈「充电估算 75%，拔线立刻 99%」，随后要求「别走电压估算，像其他设备一样自报」，
  最后定目标为「做到和 G HUB 显示一致就行」。
- **证伪硬件自报（关键结论，别再重复怀疑）**：`C343` 的 `0x0001 FEATURE SET` 全表 36 个特性，
  没有 `0x1000`/`0x1004`/`0x1F20`；唯一 `0x1001` fn0 回 `10 53 80`（4179mV+flags），
  fn1 全零、fn2/3 报 error 0x07。34 个 HID 接口无标准电量字段，Windows 无 Battery 节点，
  隐藏特性 `0x1802/0x1806` 回 error 0x05（要 `0x1E00` 写设备解锁，只读铁律不做）。
  本机没装 G HUB（只有 ProgramData\Logishrd 残留），拿不到型号专属 PowerModel。
  其他设备准是因为私有协议帧里直接带百分比字节（固件算好），G913 这代不给。
- **根因（我的锅）**：上一版「充电一律扣固定 185mV IR 抬升」错误。充电末期电流变小、
  IR 抬升趋近 0，扣 185 把 99% 压成 75%；拔线不扣又弹回 99% —— 19 点断层是人为的。
- **最终方案（对齐 G HUB 行为）**：
  - `LogitechBatteryPercent(mv, full)` 去掉 charging 参数，充放电**共用同一条曲线**，
    绝不按状态扣偏移；`full`/电压≥4186mV 对齐 100%（充满校准）。
  - `ChargingProgressLevel(anchor, elapsedMs)`：充电期间不用电压，按 180 分钟充满线性推进。
  - `LevelState` 扩展 `charging/chargeStart/chargeAnchor`；状态切换重置锚点；
    两端都过 `SmoothEstimatedLevel()` ±6 点限速，插线/拔线不瞬跳。
  - 删 `kLogiChargeIRDropMv`；`kLogiFullCharge*` 移到文件前部共享常量区（原放在后面
    匿名命名空间导致 ScanLogitech 编译报未声明）。
- 验证：自检 **57/57**；真机 `≈99% | USB 有线 | 充电中`（4179mV）；
  时间线模拟插线 73→73%、充电 48min 到 98%、拔线 99%、之后缓降。
- 若日后要逐点追平 G HUB：装 G HUB 提取 PowerModel XML，或走 `lghub_agent` 本地 WebSocket
  （社区 `LGSTrayBattery_GHUB` 就是这么干的）；当前纯本地无依赖方案不做。
- 编译前又结束了一次用户运行的 yudian.exe（21:53 启动那个），需重新双击。

## 追加：接入 G HUB 官方 PowerModel（22:35 后，最终方案）

- 用户装好了 G HUB，要求 G913-TKL 电量准确显示。
- **找到官方数据**：`C:\ProgramData\LGHUB\depots\887386\g915_tkl_us\battery.xml`
  （`<powermodel pid="0xc343">`，G913 在 G HUB 里叫 g915_tkl_us）。
  结构：`<discharge>` 每行「时间, CCV, 累计 mWh」（总 5510mWh），
  `<charging>` 每行「CCV, SoC」；**充放电是两条独立曲线**。
  4133mV：充电 83.3% / 放电 99%；3948mV：放电 76.4%。
  之前所有跳变的根源就是拿放电表算充电。
  另有 `<charging_time_slots equation_coefficiency="150">`：电压稳定 ≥4100mV 后每 150 秒涨 1%。
- 实现：
  - `app/src/logitech_powermodel.h`：151 点放电表（降序）+ 120 点充电表（升序），
    连续相同百分比压缩成区间端点；`dev/probes/extract_ghub_powermodel.py` 可重新生成。
  - `LogitechDischargePercent()` / `LogitechChargingPercent()` 查表线性插值；
    `LogitechTrickleLevel()` 做官方涓流；`full` 对齐 100%。
  - `ScanLogitech`：名字读取移到电量之前，按型号含 g913/g915 选官方表，否则用内核通用表；
    `LevelState` 改为 `{level, at, charging, trickleStart, trickleBase}`。
  - 删除自造的 `kLogiChargeIRDropMv`、`ChargingProgressLevel`、180 分钟时间模型。
- 验证：自检 **64/64**；真机 `≈100% | 4169mV | 放电中 | G HUB 官方充放电曲线`，与 G HUB 同源。
- 观察：G HUB 常驻会和我们在 HID++ 通道竞争，冷启动首轮偶发全超时（罗技 0 台），
  重扫即恢复；`live` 为空时不出休眠占位是既有设计，不是本轮回归。
- 待用户验证：插线充电时面板应显示 ~83%（4133mV）/ ~89%（4179mV），应与 G HUB 数字接近。

## 追加：面板文案区分「官方曲线」与「电压估算」（22:50 后）

- 用户问「为啥页面还显示电压估算，别的设备也是电压估算吗」。
- 原因：上一轮只在 `detail` 里写了「G HUB 官方曲线」，但面板 meta 行仍是旧的
  「· 电压估算」，且数字前带「≈」——漏改。
- 修复：`Reading` 新增 `officialCurve` 字段；G913/G915 的估算值标「· 官方曲线」、
  数字不带 ≈；其余只有电压的罗技设备仍标「· 电压估算」+「≈」。
  detail 改为「电压 4164 mV（放电中）· G HUB 官方充放电曲线」。
- 事实澄清：**别的设备不是电压估算**——迈从/飞智/索尼/Compx 的协议帧里直接带
  百分比字节，是固件算好的；G913 的 36 个 HID++ 特性里没有任何百分比通道，
  只能电压换算（G HUB 同样如此，只是它有官方表）。
- 验证：自检 64/64；面板 `G913 TKL | 100% | 放电中 · 官方曲线`，截图确认无 ≈、不截断。
