## 修复：点通知的 × 会弹出面板

- 根因：`ToastProc` 里 `g_toastCloseRect` 记的是**卡片坐标**（`DrawToastContent` 在
  `TranslateTransform(m, m+slide)` 之后画），鼠标 `pt` 是**窗口客户区坐标**。分层窗口
  带 36 DIP 阴影余量后两者差 54px（150%），点可见的 × 永远落在热区外 → `onClose=false`
  → `PostMessage(WM_APP+5)` → `UiTogglePanel()`。
- 同一偏差导致悬停高亮画在卡片左上方的阴影里，从没落在 × 上。
- 修法：`ToastCardPoint()` 把鼠标点翻回卡片坐标（减 `ShadowPx()` 与 `g_toastSlide`），
  `WM_MOUSEMOVE`/`WM_LBUTTONUP` 共用；再给「叫面板」加 `inCard` 护栏，卡片外点击只关通知。
- 验证：`SendInput` 真实点击 —— 修复前点 × 面板弹出（复现），修复后点 × 只关通知、
  点正文仍开面板、点阴影只关、悬停高亮居中于 ×（半径≈17px 圆盘）、6s 自动消失不受影响。
- 回归：28 警告、--shot/--shot-toast/--list 正常、提示窗开着退出 0.05s。
- 记录：`docs/reviews/2026-10-29-fixes.md` 第十一节。

  报 `expected LP_HIDP_CAPS instance`；应复用 `H.hidprobe.HIDP_CAPS`。
- 待办：用户插上接收器/配对蓝牙后跑 `battery_scan.py`；若有 0x06/0x20 → 需要把通用 HID 取数

## 雷柏 M200 实测（接收器 24AE:2015）

- 接口：0001/0000(FEA=8)、0001/0002(鼠标)、0001/0006(键盘)、0001/0080、000C/0001、
  **FF00/000E(IN/OUT=32, report 0xBA)**。
- `battery_scan.py`：无 0x06/0x20 标准电量字段；鼠标/键盘集合只能 `access=0` 打开（Windows 保护），
  读不了输入报告，VT3 那种“被动收 13 字节报文”的路子走不通。
- 公开协议（OpenMouse `@openmouse/protocol/rapoo` dist）：0xBA 帧 =
  `[conn][cmd][len][addr u32][data...]`，cmd 0xA4 读/0xA5 写/0xAA 电量；
  **应答走 GET_REPORT(Input) → Windows `HidD_GetInputReport`**，不是 ReadFile 队列；
  电量帧 `[status=1][marker 1/2][percent]`。
- 实测：`a3` 握手、`0x880` 性能寄存器、`0xAA` 电量——**三种命令全部无应答**（SetOutputReport 与
  WriteFile 都试过，连接字节 a5/ff/00/01/5a 都试过）。所以要么鼠标本体在休眠，要么办公系
  接收器不实现这条通道。
- 唯一可读：`0001/0000` 的特性报告 0x05 = `04 55 91 01 00 00 00 00`，恒定不变（写入也被接受但无效果）。
  疑似 `[85%][1.45V][link=1]`，与 AA 碱性电池吻合，但**语义未验证**，不能直接当读数。
- 新增 `dev/probes/rapoo_probe.py`（只读探测，已登记 README）；`battery_scan.py` 同批新增。
- 下一步：确认鼠标电源状态（关掉再开、晃两下）后重跑 `rapoo_probe.py`；仍无应答则判定该型号
  不提供可读电量，代码层不加“假支持”。

### 采样结论（14:39-14:40）

- 鼠标持续活动 54 秒（`GetLastInputInfo` 每 0.2s 都变），特性报告 0x05 **始终是 `04 55 91 01 00 00 00 00`**，零变化。
- 若是活电压，移动时应有 1~5 个单位的下沉；完全没有 → 这份报告是**静态信息**（版本/能力），
  不是电池状态。`85% / 1.45V` 的解读不成立，不能接进读数。
- 2.4G 接收器对该协议（a3/a4/aa）持续无应答 → 判定：**M200 系列 2.4G 模式不提供可读电量**。
- 剩余可能：蓝牙 4.0 模式若暴露 GATT 0x180F，程序的 BLE 路径可直接读，无需改代码。

## 新建 token-panel：WorkBuddy Token 实时用量面板

- 位置 `token-panel/`，纯 Python 3 标准库 + 本地 echarts，零 pip 依赖；只读 `~/.workbuddy`，不写任何 WorkBuddy 数据。
- **数据源踩坑**：内置 `token-usage` 技能默认读 `~/.codebuddy/projects`，本机实际在
  `~/.workbuddy/projects`（67 个 jsonl / 347MB）。转录里 `providerData.usage` 为 camelCase，
  `message.usage` 为 snake_case，两者并存只能计一次；`timestamp` 是**毫秒**。
- **口径**：轮数 = `COUNT(DISTINCT conversationRequestId)`，不是记录条数——一次提问可触发几十次模型调用。
  实测 1 轮可对上 66 次调用。`session_usage.used/size` 是**上下文占用**，不是累计 token，不能当消耗量。
  缓存命中率常年 98%+，总量 41 亿里 40 亿是缓存，所以面板把命中率单独做成一张卡，避免被总数误导。
- **当前会话识别**：`sessions/*.json` 里有伪会话 `sessionId=interactive-<pid>`（cwd 指向 Temp），
  心跳还最新，会顶掉真会话。改为以"谁正在产生 usage 事件"为准，心跳只用于补 cwd，并加 uuid 正则过滤。
- **credit**：`credit_json` 的 key 就是 `conversationRequestId` 去连字符，实测 371/392 可对上（94.7%）。
  中途用 5 个老 key 验证命中 0/5，是**假阴性**（那些会话转录已清理），差点误判 mapping 不成立。
  读 `workbuddy.db` 用 `mode=ro`，失败退 `immutable=1` 并标"可能滞后"，再失败就显示"不可用"，不影响 token。
- **索引**：SQLite 存每文件字节位点，冷启 1.2~1.8s，稳态轮询 p50 25ms / p95 31ms。
  四条边界全测：半行未写完不消费、截断重写清空重读、inode 变重建、超长行跳过。
- **Windows 坑**：`os.stat().st_ino` 是 128 位，直接入库 `OverflowError`，必须 `& 0x7FFFFFFFFFFFFFFF`。
- **环境限制**：`reg.exe` 与 `WScript.Shell` COM 都被本机安全策略黑名单，注册表自启走不通；
  改为在用户启动文件夹放 `token-panel.cmd`（用 `mbcs` 编码写中文路径），无需管理员、删文件即撤销。
- **无头截图坑**：SSE 长连接让页面永不 idle，`--virtual-time-budget` 会让渲染进程崩；
  改用 `timeout 25 chrome --headless --screenshot`，并加 `?static=1`（关动画、不连 SSE）用于离线快照与截图核对。
- 首屏由服务端把数据注入 HTML（`__BOOT__` 占位），避免打开瞬间一片空白。
- 验收：selftest 24 项全绿；索引与独立全量扫描逐项一致（条数/总量/input/output/cache 完全相同）。

## token-panel 降耗改造：待机降频 + credit 指纹 + 日志降噪

- 背景：用户发现“后台任务一直在跑”。排查确认是 18:41 用**会话后台任务**方式拉起的面板本体
  （PID 16236，44MB，3h40m 累计 CPU 378s ≈ 单核 2.9%），不是自动化任务（列表为空）。
- CPU 全在 `discover()`：os.walk 67 文件 + stat 约 25-35ms，每秒一次 ≈ 3%。
- 改动：`Indexer` 注入 `is_active` 回调（不反向 import server）+ `_wake` Event + 1s 分片等待，
  无 SSE 客户端时 1s→5s；`progress` 所有键在 `__init__` 建齐（HTTP 线程 `dict()` 拷贝，
  运行期加键会 `RuntimeError`）；checkpoint 从 `tick%300` 改按时间 300s（否则降频后变 25 分钟）。
- credit 判据**不能用 mtime**：WAL 下主库时间戳滞后，NTFS 对打开中的文件时间戳也惰性更新，
  假阴性会让 credit 永久卡旧值。改用开库后一条聚合指纹（count/max(updated_at)/sum(length)/sum(used)/sum(size)），
  未变则跳过；`lag=True`（immutable 降级）永不跳过，否则锁死降级态；成功后 600s 内不再全量。实测 16ms → 1ms。
- 日志噪音根因：`ConnectionAbortedError` 不属 BrokenPipe/ConnectionReset，穿透到 `do_GET` 兜底，
  既打堆栈又往坏 socket 补 500。加 `CLIENT_GONE = ConnectionError` + `_begin/_body` 原语 +
  `_responded` 位；移除 `_stream` 里过宽的 `OSError`。23 次中断连接零新增堆栈，真异常仍 500+完整堆栈。
- 实测：待机 CPU **2.94% → 0.62%**（-79%），扫描 60→12 次/分；有客户端时立即回 1.0s（10 秒 10 次）；
  selftest 24/24；bench p50 26.7ms / p95 30.0ms；stop-panel.bat 318ms 退出并清 pid。
- Windows 坑：`reg.exe`、`WScript.Shell` COM 均在本机黑名单（自启只能放启动文件夹）；
  从 bash 调 `cmd /c start` 会被工具判为长驻而 SIGTERM；`/D` 参数被 Git Bash 路径转换吃掉。
  最终用 Python `subprocess.Popen(creationflags=DETACHED_PROCESS|CREATE_NO_WINDOW, stdio=DEVNULL)` 脱离，
  父进程已退出、全系统仅剩一个 pythonw（PID 11268）。
- 回滚备份：`.workbuddy/backup/token-panel-20261102/`（config/indexer/server/credit 四个文件）。

## 桌面入口：Token 面板.cmd

- 用户选择"桌面快捷方式"而非开机自启。但本机 `reg.exe` 与 `WScript.Shell` COM 均在黑名单，
  **无法生成 .lnk**，只能用批处理入口（代价：黑框闪一下、无自定义图标）。
- 踩坑：第一版把中文路径直接写进 `start` 行（cp936 编码），能读回但**任何含中文的 .cmd 都依赖控制台代码页**；
  验证脚本里一条中文 `rem` 就被 cmd 按 cp936 解析后当命令执行报错，坐实了这个风险。
- 终版改为**纯 ASCII**（0 个非 ASCII 字节）：用 `for /d %%d in ("D:\WorkBuddy\*")` 通配符在运行时解析
  中文目录名，彻底绕开编码。验证脚本用同样逻辑只 echo 不启动，输出 `RESOLVED_OK`。
- 另一坑：从 bash 传中文参数给 `cmd //c` 会失败（bash UTF-8 vs cmd cp936），
  `cmd //c type "中文名.cmd"` 报"找不到路径"是桥接问题，不是文件问题——验证要走通配符或 Python。
- 结论：智能体起的进程（含 DETACHED_PROCESS）会在会话结束后被回收，持久运行只能用户自己双击。

## G304 电量 90% / 耗尽仍 20% 的排查与修复

- 实测 HID++：`0x1000` 返回 `5a 32`，参数[0]=90 是**设备直报**；`0x1001` 不支持，拿不到电压。
  程序对罗技**没有任何电压→百分比换算**，只在 >100 时掩码 &0x7F（90 不触发）。
- 结论：90% 与「20% 后突然断电」是 G304 固件电量计特性（红灯慢闪≈15~20%），不是本程序误差。
- 真正的 bug：`MergeReading` 无条件沿用旧百分比 → 电池耗尽后 20% 永久挂着；
  `CheckLowBattery` 又拿 stale 值报警。
- 修复：沿用上限 15 分钟，超时 level=-1/状态「长时间无响应」/detail 留最后读数；
  低电量提醒跳过 stale。`merge_test.cpp` 16 条断言全过；--list 仍 90%；28 警告；626,688 B。
- 注意：重建时结束了正在运行的实例（PID 29480），需重新启动。
