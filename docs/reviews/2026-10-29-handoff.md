## 1. 结论摘要

### 1.1 最高优先级（先修这些）

| 编号 | 问题 | 影响 | 置信度 |
|---|---|---|---|
| C1 | 通用 HID 在 `reportId=0` 时没有跳过 Feature 缓冲区首字节 | 电量整体错位 8 bit，可能把满电读成 0% 并触发低电量提醒 | 高，源码路径明确 |
| C2 | 通用 HID 没有按 `logicalMin/logicalMax` 归一化 | 0..1、0..10 等合法描述符会显示成 1%/10% | 高 |
| C3 | 设备身份过度依赖 VID:PID | 两只同型号手柄/两个同型号接收器被合并成一条，读数互相覆盖 | 高，设计层面明确 |
| C4 | 迈从 V2 用 `featureLen` 判断接口，但协议实际走输出报告 | 某些合法的“OUT=64、FEATURE=0”接口不会被选中，设备读不到 | 中高，需真机/构造 HidInfo 验证 |
| C5 | BLE 结果每 8 轮才刷新，却被每轮标记为当前时间的在线数据 | 默认 2 分钟间隔下，BLE 实际约 16 分钟才更新；旧值掩盖掉线 | 高 |
| C6 | 休眠占位记录覆盖最后一次有效电量 | 与 README 的“保留最后读数”承诺不一致 | 高 |

### 1.2 次要但应修

- 罗技空通道错误帧被当成“确认存在过”，会制造幽灵休眠设备。
- 面板 DIB 在仍选入 DC 时被 `DeleteObject`，反复改变尺寸可能泄漏 GDI 对象。
- 扫描线程退出只等 1.5 秒且不检查结果，之后继续销毁共享状态，存在退出竞态。
- 迈从 V2 应答没有验证 XOR 校验。
- `AutostartSet` 忽略注册表失败，UI 可能显示“已开启”但实际未生效。
- 手动全量刷新可能被随后到达的普通刷新降级。
- 罗技设备名/品类缓存不会随通道更换设备而失效。
- Python 公共探针的异步取消存在缓冲区/事件生命周期风险。
- `ble_batt.py` 的 `BluetoothGATTGetCharacteristicValue` 参数个数和真实 API 不一致。

### 1.3 总体评价

代码不是“随便拼出来的原型”：

- 协议边界检查总体比一般 HID 小工具严谨，Compx/MCHOSE V1 有校验和状态判断。
- 异步读写有 `CancelIoEx` + 等待完成的意识，主程序没有直接 `TerminateThread`。
- UI 的 DPI、分层窗口预乘 alpha、阴影缓存、主题切换、滚动和命中测试有明显工程投入。
- 单实例、消息所有权、托盘重建、配置范围归一化等常驻程序细节考虑较完整。

但当前质量瓶颈集中在三处：

1. **通用协议抽象不够“按描述符正确解析”**，容易被 report ID、logical range 和多 usage 字段击穿。
2. **设备身份模型是“型号级”而不是“物理设备级”**，多设备场景会合并错误。
3. **调试探针没有形成可靠基础设施**：50 个脚本共享一个公共库，但公共库的异步 I/O 和 API 声明仍有高风险问题。

## 2. C++ 主程序审查

### C1（高）通用 HID `reportId=0` 解析偏移错误

**位置**

- `src/hid.cpp:310-316`
- `src/providers.cpp:1932-1939`

**证据**

`GetFeature()` 明确把报表 ID 放在 `buf[0]`：

```cpp
buf.assign(len, 0);
buf[0] = reportId;
if (!HidD_GetFeature(handle_, buf.data(), len)) return false;
```

但解析时只有 `reportId != 0` 才跳过首字节：

```cpp
const uint8_t* body = buf.data();
int bodyLen = (int)buf.size();
if (bf.reportId != 0 && buf[0] == bf.reportId) {
    body = buf.data() + 1;
    bodyLen -= 1;
}
int raw = ExtractBits(body, bodyLen, bf.bitOffset, bf.bitSize);
```

Windows 的 HID Feature 缓冲区无论设备是否使用 Report ID，首字节都是 Report ID；不使用 Report ID 时该字节为 0。描述符中的 `bitOffset` 是相对报表数据区，不包含这个字节。

**触发条件**

使用标准 HID Battery Feature、且描述符没有 Report ID（`reportId=0`）的设备。

**影响**

所有字段偏移整体错 8 bit。典型 `offset=0, size=8` 会把首字节 0 当成电量，显示 0%，并可能触发低电量 toast。

**最小修复**

成功取得报表后，始终跳过 `buf[0]`：

```cpp
if (buf.empty()) return;                 // 或 continue
const uint8_t* body = buf.data() + 1;
int bodyLen = (int)buf.size() - 1;
```

同时确认 `HidD_GetFeature` 返回长度与实际 `featureLen` 一致，再做解析。

**建议测试**

- `reportId=0`，返回字节 `[0, 100]`，字段 offset=0/size=8 → 100%
- `reportId=5`，返回字节 `[5, 100]` → 100%
- 截断报文、零长度、只有 Report ID 的报文 → 不产生读数

### C2（高）通用 HID 没有按 logical range 归一化

**位置**

- `src/providers.cpp:1893-1898`
- 调用点 `src/providers.cpp:1939-1941`
- `BatteryField` 已保存 `logicalMin`，见 `src/hid.h:46-52`

**证据**

```cpp
int NormalizeLevel(int value, int logicalMax) {
    int hi = logicalMax > 0 ? logicalMax : 100;
    if (value < 0) return -1;
    if (hi <= 100) return std::min(100, value);
    if (hi <= 255) return std::min(100, (int)((value * 100 + hi / 2) / hi));
    return -1;
}
```

当 `logicalMax <= 100` 时直接把原始值当百分比，完全忽略 `logicalMin`。

**触发条件**

描述符声明 0..1、0..10、10..20、0..255 等范围，或 `logicalMin != 0`。

**影响**

- 0..1 满电显示 1%
- 0..10 满电显示 10%
- 10..20 的中间值显示 10~20%
- 这些错误会进一步触发低电量提醒

**最小修复**

```cpp
int NormalizeLevel(int value, int minValue, int maxValue) {
    if (maxValue <= minValue || value < minValue || value > maxValue) return -1;
    long long num = (long long)(value - minValue) * 100;
    return (int)((num + (maxValue - minValue) / 2) / (maxValue - minValue));
}
```

调用处传 `bf.logicalMin` 和 `bf.logicalMax`，并限制结果在 0..100。

**建议测试**

对 0..1、0..10、0..100、0..255、10..20 的最小值、中点、最大值和越界值做表驱动测试。

### C3（高）同型号多台物理设备被 VID:PID 合并

**位置**

- 索尼：`src/providers.cpp:1745-1775`
- 飞智：`src/providers.cpp:1342-1369`
- 迈从：`src/providers.cpp:1238-1267`
- Nordic54：`src/providers.cpp:1184-1200`
- 通用 HID：`src/providers.cpp:1943-1947`
- 合并覆盖：`src/main.cpp:61-89`（`devices[r.key] = r`）

**证据**

索尼按 PID 分组：

```cpp
std::map<uint16_t, std::vector<const HidInfo*>> byPid;
...
r.key = L"sony:" + std::to_wstring(d.pid);
```

飞智按 VID:PID 分组并生成同粒度 key；迈从虽然按“VID:PID + 产品名”分组，但 `Reading::key` 仍然只有 VID:PID：

```cpp
std::wstring key = L"mchose:" + std::to_wstring(d0.vid) + L":" +
                   std::to_wstring(d0.pid);
```

**触发条件**

- 同时连接两只 DualSense / DualShock
- 同时插两个同型号接收器
- 两只同型号飞智手柄
- 同型号同名的两个通用 HID 设备

**影响**

接口被混在同一组里，只选其中一个读取；最终面板只显示一条。迈从不同产品组还可能生成相同 key，在 `MonitorState` 中互相覆盖。

**最小修复**

物理设备身份应优先使用：

1. 设备 ContainerId
2. 序列号
3. 接口根路径（去掉 `&colNN` 等集合后缀）
4. 最后才回退到 VID:PID + 产品名

USB/蓝牙双路径去重不应只靠 VID:PID；可用 ContainerId 判定“同一物理设备”，用接口根路径区分“同型号的不同设备”。

**建议测试**

- 两组同 VID:PID、不同接口根路径的模拟设备 → 必须生成两条稳定记录
- 同一设备暴露多个 HID 集合 → 仍只生成一条记录
- 同一设备 USB + BT 同时存在 → 合并成一条，USB 优先

### C4（中高）迈从 V2 用 Feature 长度识别 Output Report 接口

**位置**

- 选择逻辑：`src/providers.cpp:1253-1256`
- 诊断标签：`src/providers.cpp:1699-1704`
- 实际写入：`src/providers.cpp:899-917`，使用 `WriteFile` 到 report `0x4D`

**证据**

```cpp
if (!v2 && d.featureLen >= MCHOSE_V2_LEN && d.usagePage >= 0xFF00) v2 = &d;
```

但协议实际走的是 64 字节 **Output Report**，不是 Feature Report。

**触发条件**

V2 集合的 `OutputReportByteLength >= 64`，但 `FeatureReportByteLength` 为 0/1（合法且常见的 HID 形态）。

**影响**

`v2` 为空，随后 V1/legacy 也不匹配，设备显示“设备休眠/接口被占用”，实际是接口选错。通用 HID 又会因为 `LooksLikeMchose()` 跳过它，导致两条路都堵死。

**最小修复**

使用 `d.outputLen >= MCHOSE_V2_LEN`，并结合 usage page/report 形态判断；`--dump` 的诊断条件同步修改。

**建议测试**

- `featureLen=0, outputLen=64, usagePage=0xFF01` → 必须选中 V2
- 只有 64 字节 Feature、没有足够 Output 的接口 → 不得误选 V2
- 真实 A5 V3 的 `--dump` 输出应能验证选择结果

> 备注：现有 A5 V3 在作者机器上能读，说明该设备可能同时报告了 64 字节 Feature；这不否定代码使用了错误判据，只是说明当前设备恰好绕过了问题。

### C5（中高）BLE 缓存被错误标记为“当前在线数据”

**位置**

- BLE 读取节流：`src/providers.cpp:1599-1631`
- 全量扫描周期：`src/providers.cpp:2080-2085`
- 合并时刷新时间和在线状态：`src/main.cpp:61-89`

**证据**

```cpp
if (g_fullSweep || !scanned) {
    ...
    cache.push_back(r);
}
for (const auto& r : cache) out->push_back(r);
```

`g_fullSweep` 约每 8 轮一次，而 `MonitorState::Scan()` 对所有 fresh 记录执行：

```cpp
r.online = true;
r.updated = now;
devices[r.key] = r;
```

**影响**

- 默认 2 分钟间隔：BLE 实际约 16 分钟才更新一次
- 30 分钟间隔：约 4 小时才更新一次
- 设备已掉线/耗尽时，UI 仍显示旧百分比、当前更新时间和在线状态
- 用户无法分辨“刚读到”和“缓存值”

**最小修复**

- 给 BLE 缓存保存 `sampledAt`，每轮只更新 `Reading` 的显示年龄，不伪造 `updated`
- 超过明确 freshness 阈值后标为“缓存/过期”或离线
- BLE 使用独立刷新周期，不与 HID 全量扫描绑定

**建议测试**

用可注入时钟推进 8 个扫描周期，确认 BLE 的实际读取次数和 UI 时间戳。

### C6（中高）休眠占位覆盖最后一次有效读数

**位置**

- `src/main.cpp:61-89`
- 罗技休眠占位：`src/providers.cpp:412-441`
- Compx 占位：`src/providers.cpp:1155-1164`
- 迈从缓存到期路径：`src/providers.cpp:1298-1335`

**触发条件**

设备先成功返回电量，随后休眠/不再应答，扫描结果产生同 key 的 `level=-1` 占位记录。

**影响**

`devices[r.key] = r` 立即用空读数覆盖之前的有效百分比、充电状态和 `updated`。README 说“保留最后一次读数”，实际显示 `--`，年龄也被重置。迈从在 90 秒缓存到期后同样会丢失旧值。

**最小修复**

在 `MonitorState::Scan()` 合并时：

- 如果新记录是明确的休眠/未应答占位，且旧记录有有效 `level`，保留旧 `level`、`voltage`、`charging` 和原始 `updated`
- 增加 `cached` / `staleSince` 字段，明确告诉 UI 这是旧读数
- 只有设备真正消失或新记录明确报告有效值时，才替换数值

**建议测试**

输入“80% 有效样本 → 休眠占位”，第二条仍应显示 80%，年龄应从有效样本时间开始计算。

### C7（中高）罗技空通道错误帧造成幽灵休眠设备

**位置**

- 错误帧返回成功：`src/providers.cpp:128-135`
- 扫描过早标记 live：`src/providers.cpp:345-354`
- 休眠占位生成：`src/providers.cpp:418-441`

**证据**

`Request()` 对 HID++ 错误帧返回 `true`，但 `r.ok=false`。扫描逻辑在检查 `probe.ok` 之前就执行：

```cpp
silent[idxI] = false;
answeredHere++;
live.insert(idxI);
if (!probe.ok) continue;
```

**触发条件**

通道先返回错误码 `0x08`（无配对设备）或其他错误，下一轮超时。

**影响**

从未存在有效设备的通道被记为“确认存在过”，之后超时就会生成“设备休眠”行，正是注释声称要避免的幽灵设备。

**最小修复**

只有 `probe.ok` 且取得有效协议应答时才加入 live；`0x08` 应清除该通道的 live 和名字缓存。

**建议测试**

“错误 0x08 → 超时”必须始终没有设备行；“有效应答 → 超时”才允许出现休眠行。

### C8（中）同一 Main Item 内电池 Usage 不在第一项时读错字段

**位置**

- `src/hid.cpp:123-134`
- `src/hid.cpp:39-44`
- `src/hid.cpp:294-306`

**证据**

一个 `ReportField` 保存整个 `usages` 数组，但 `bitOffset` 只指向该 Main Item 的第一个子字段。`isBattery()` 只要任一 usage 匹配就返回 true，`FindBattery()` 没有记录匹配的是第几项。

**触发条件**

一个 Feature Main Item 包含多个 8 位字段，例如 `usages=[其他状态, BatteryStrength]`。

**影响**

- 对 Usage Min/Max 也要保留展开后的索引

**建议测试**

### C9（中）迈从 V2 应答没有验证 XOR 校验

**位置**

- 组帧和校验位置：`src/providers.cpp:876-894`
- 解析：`src/providers.cpp:924-945`

**证据**

组帧写入了 `f[8+n] = cs`，但接收解析只检查：

uint8_t cs = 0;

**建议测试**

### C10（中）面板 DIB 销毁顺序可能泄漏 GDI 对象

**位置**

- `src/ui.cpp:808-839`

**证据**

```cpp
void DestroySurface() {

    if (g_surface.dc) DeleteDC(g_surface.dc);

bool EnsureSurface(int w, int h) {

```

**最小修复**

在创建时保存 `HGDIOBJ old = SelectObject(dc, dib)`；销毁时先恢复：

```cpp
if (g_surface.dc) {
    if (g_surface.old) SelectObject(g_surface.dc, g_surface.old);
    DeleteDC(g_surface.dc);
}
if (g_surface.dib) DeleteObject(g_surface.dib);
```

或者先 `DeleteDC` 再 `DeleteObject`，但保存/恢复选入对象更明确。

**建议测试**

### C11（中）扫描线程生命周期没有可靠有界退出

**位置**

### C12（中，安全加固）描述符整数边界和位提取 UB

**位置**

- `src/hid.cpp:50-57`、`src/hid.cpp:98-134`
- `src/providers.cpp:1882-1890`

**证据**

- `reportSize`、`reportCount` 来自设备描述符，使用 `int` 保存
- `f.bitOffset + g.reportSize * g.reportCount` 没有 checked arithmetic
- `ExtractBits` 只检查 `byteIdx >= payloadLen`，没有检查 `byteIdx < 0`
- 对任意 `bitSize` 执行 `value |= (1 << k)`，`k=31` 时是有符号左移 UB

**触发条件**

畸形/恶意 HID 描述符声明极大 count、负 offset 或 31/32 位字段。

**影响**

负索引可在缓冲区前读取；有符号溢出和大位移是 C++ 未定义行为，可能崩溃。  
**不要把它描述成远程可利用漏洞**：前提是本地恶意设备或驱动，属于健壮性/安全加固问题。

**最小修复**

- 使用 `size_t`/`uint32_t` + checked arithmetic 限制 total bits、count、offset、size
- 对 `bitOffset < 0`、`bitSize <= 0`、`bitSize > 32` 直接拒绝
- 使用无符号移位并显式限制位宽；更稳妥的是按 byte 读取后组合
- 对描述符总长度设上限（例如 4096），对 usage 展开数量设上限

**建议测试**

对 `ParseDescriptor` + `ExtractBits` 做模糊测试：0xFFFFFFFF count/size、截断长条目、32/64 位字段；在 ASan/UBSan 下运行。

## 3. Python 探针审查

### P1（高）异步读写超时后释放缓冲区和事件过早

**位置**

- `probe-tools/hidprobe.py:218-259`

**证据**

```python
rc = kernel32.WaitForSingleObject(ev, timeout_ms)
if rc != WAIT_OBJECT_0:
    kernel32.CancelIo(h)
    kernel32.CloseHandle(ev)
    return None
```

超时后只调用 `CancelIo`，立即关闭事件并返回；没有 `GetOverlappedResult(..., TRUE)` 等待 I/O 真正结束。此时内核仍可能持有 `OVERLAPPED`、事件或读缓冲区指针，Python 局部对象随后被回收，形成 use-after-free/未定义行为。

**影响**

所有使用 `_read_timeout` / `_write_timeout` 的脚本都可能偶发崩溃、卡死或读到未定义数据；设备无响应时最容易触发。

**最小修复**

- 使用 `CancelIoEx(h, byref(ov))`
- 超时后必须 `GetOverlappedResult(h, byref(ov), byref(got), True)` 等待完成
- 再关闭事件、返回
- 为 `OVERLAPPED` 使用稳定内存，不要在 I/O 未完成时让 Python 对象被回收
- 增加 `ERROR_OPERATION_ABORTED` 分支

**建议测试**

用不会回包的 HID 接口或 mock handle 反复触发超时，在 Application Verifier/ASan 下运行。

### P5（中）固定 512 字符的 DevicePath 结构可能截断或越界写入

**位置**

- `probe-tools/hidprobe.py:40-41`
- `probe-tools/ble_batt.py:47-48`
- 调用处按 `need` 作为缓冲区大小传入

**证据**

```python
class SP_DEVICE_INTERFACE_DETAIL_DATA_W(ctypes.Structure):
    _fields_ = [("cbSize", wt.DWORD), ("DevicePath", ctypes.c_wchar * 512)]
```

API 的 `DevicePath` 是变长数组；当前结构只有 512 个 wchar。若系统返回的 `need` 大于结构实际大小，API 仍按调用方传入的 `need` 写入，存在越界风险；若传入结构大小，则长路径会失败。
