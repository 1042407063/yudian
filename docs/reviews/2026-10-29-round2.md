## 3. 本轮新发现

### 3.1 高

#### N1（高）`hidprobe.xfer` 在异步句柄上用 NULL OVERLAPPED 写，`send` 子命令本身不可靠

- **位置**：`probe-tools/hidprobe.py:301`、`:306-313`
- **事实**：`h = _open(path, overlapped=True)` 打开的是 `FILE_FLAG_OVERLAPPED` 句柄，随后：
  - `feature` 分支调用 `HidD_SetFeature(h, ...)`；
  - `write` 分支调用 `WriteFile(h, buf, len, &written, None)`。
- **为什么错**：`lpOverlapped` 为 NULL 时，对 overlapped 句柄的 I/O 语义未定义（可能同步完成、可能 `ERROR_INVALID_PARAMETER`，也可能与后续 `ReadFile` 竞争同一管道）；`HidD_SetFeature` / `HidD_GetFeature` 按文档要求句柄**不得**带 `FILE_FLAG_OVERLAPPED`。
- **影响**：`python hidprobe.py send ...` 是本目录的"标准入口"，它给出的"写失败/无回包"结论不可信，会把正确帧判成错误帧。同一文件里 `listen` 分支没有问题（只读）。
- **改进方向**：`xfer` 改成双句柄——同步句柄写、异步句柄读，与 `v2_out.py` / `probe3.py` 已验证的写法一致；`via=feature` 单独开一个非 overlapped 句柄。

#### N2（高）`caps.py` 的 `HIDP_VALUE_CAPS` 布局错误，输出的位宽/范围全是错的

- **位置**：`probe-tools/caps.py:10-25`
- **事实**：`IsRange / IsStringRange / IsDesignatorRange / IsAbsolute` 四个字段在 `hidpi.h` 里是 `BOOLEAN`（1 字节），脚本声明成 `wt.USHORT`（2 字节）。
- **实测**：`sizeof` = **76**，Windows 真实结构 = **72**。`BitSize` 实际在偏移 18，脚本读偏移 22；`LogicalMin` 实际 40，脚本读 44。
- **影响**：这是仓库里**唯一**用系统 API 读 Value Caps 的工具，它输出的 `bits=/count=/lmin=/lmax=` 全部错位。任何据此得出的"某字段是 8 位 / 范围 0..100"的结论都要重做。它恰好也是排查 C2、C8 最需要的工具。
- **改进方向**：四个字段改成 `ctypes.c_ubyte`；补 `_pack_` 校验（`assert ctypes.sizeof(...) == 72`）；顺带删掉 `:27` 的 `if False else` 死代码和 `:46-47` 的空循环。

### 3.2 中高

#### N3（中高）9 个脚本"单异步句柄既写又读"，产出的否定结论可能是假阴性

- **位置**：`scan13.py:14`、`scanrid.py:9`、`scanrid2.py:9`、`variants.py:10`、`matrix2.py:10`、`cmdscan.py:10`、`cmdread.py:13`、`ask.py:12`、`probe_matrix.py:72`
- **事实**：这些脚本用同一个 `_open(path, overlapped=True)` 句柄做 `_write_timeout` 和 `_read_timeout`。而 README 自己的结论第 5 条就是"写和读不要共用一个异步句柄，否则输入管道静默，表现像设备休眠"。
- **影响**：`scan13.py`（V1 子命令扫描）、`scanrid*.py`（report id 枚举）、`matrix2.py`（帧布局对照）都是靠"有没有回包"下结论的实验。用已知会静默的方法做扫描，得到的"无回包"不能证明协议不支持。**这些脚本产出的历史负面结论需要用双句柄重跑一遍才能关闭。**
- **改进方向**：统一改用 `hw = _open(path)` + `hr = _open(path, overlapped=True)`；在脚本首行注明"此脚本为历史方法，结论已失效"。

#### N4（中高）10 个脚本解析回包不做长度校验，非目标帧会直接抛 `IndexError`

- **位置**：`v2_out.py:43-50`、`mch_v2.py:43`、`loop_v2.py:34-40`、`loop_v2b.py:40-47`、`sweep.py:59-67`、`v2_feat.py:45`、`poll_bat.py:44`、`crossif.py:40-43`、`probe_final.py:110`、`sony_usb2.py:15`
- **事实**：典型写法是先认帧头再直接取偏移：
  ```python
  if d[0] == 0x4D and d[4] == 0x00 and d[5] == 0x09:
      n = d[3]; data = d[8:8+n]
      if n >= 13: print(f"电量={data[12]}%")     # data 可能不足 13 字节
  ```
  `data = d[8:8+n]` 在报文被截断时会**静默变短**，`data[12]` 随即 `IndexError`。`d[0]`/`d[4]`/`d[5]` 更是连"报文至少 6 字节"都没判。
- **影响**：设备返回心跳帧、短帧或噪声时脚本崩溃，看起来像"设备异常"，实际是解析器太脆；`sony_usb2.py:15` 在 `0x01` 报文短于 55 字节时必崩。
- **改进方向**：抽出 `def v2_payload(d): return d[8:8+d[3]] if len(d) >= 9 + d[3] else None`，所有偏移访问前先判 `len`。

### 3.3 中

#### N5（中）`ask.py` 的校验计算会越界索引

- **位置**：`probe-tools/ask.py:36-37`
- **事实**：`body = d[:LEN]`；`body[LEN - 1]`。当实际读回长度小于 `LEN`（`ReadFile` 只返回该接口真实报告长度），`body[LEN-1]` 越界。
- **影响**：0x4D 这类 64 字节帧配 33 字节输入报文时必崩；崩溃点在"校验"这一步，会让人误以为是设备校验不过。
- **改进方向**：`if len(d) < LEN: print("短帧", len(d)); continue`。

#### N6（中）飞智三个脚本不校验帧头就按固定偏移解析

- **位置**：`flydigi2.py:31-35`、`flydigi3.py:23-25`、`flydigi4.py:32-34`
- **事实**：取**第一条**读到的帧（可能是心跳、按键帧）就当作 `5A A5` 应答，直接读 `f[5]/f[6]/f[11]/f[31]`。
- **影响**："隔一次才应答"这个关键结论正是这几个脚本得出的；但它们没有确认手上这帧是不是应答，因此"应答率 3/6""6/6 成功"的统计口径存疑。
- **改进方向**：先 `if got[1:3] != b"\x5a\xa5": continue`，再按 `f[4]` 的总长校验 `len(f) >= 32`。

#### N7（中）`featscan*.py` 对 0..0x3F 每个特性 ID 盲写全零

- **位置**：`featscan.py:17-20`、`featscan2.py:18-21`
- **事实**：对每个 report id 都执行 `HidD_SetFeature(全零)`，只把"返回成功"记为"可 Set"。
- **影响**：这已经超出"读"的范畴。HID 特性报告里常见 LED、灵敏度档位、模式开关；对未知 ID 写全零可能把设备改到某个状态（`featscan2` 覆盖到 `0x40–0x60`，正是 0x4D 所在区间）。README 写的"只读为主"与实现不符。
- **改进方向**：把 Set 扫描拆成独立脚本并加 `--yes` 确认；默认只做 Get；README 按"只读 / 会写设备 / 会杀进程"三类标注（对应上一轮 P7）。

#### N8（中）16 个脚本硬编码 VID:PID，设备不在就 `IndexError`

- **位置**：`classic.py`、`crossif.py`、`flydigi*.py`(4)、`sony_*.py`(7)、`namescan.py`、`regscan.py`、`regscan2.py`
- **事实**：`H.find("37D7:2401", "FFA0:0001")[0]`；`rows[0]`（`sony_usb.py:7`、`sony_usb2.py:7`）在过滤结果为空时同样崩。
- **影响**：换一台设备或换一个接口形态，脚本立刻死在第一行，没有任何"我要找什么、实际找到什么"的提示。
- **改进方向**：改成 `argv` 传入 + `require_one()` 包装（上一轮 P6 已给过实现）。

## 5. 优化建议

### 5.1 第一优先：把"读数链路"修到可验证

**（1）通用 HID 解析重写为"按描述符展开 + 统一偏移基准"** — 一次改动同时关闭 C1、C2、C8、C12。

- 定位：`hid.cpp:121-141`（`ParseDescriptor`）、`hid.cpp:294-308`（`FindBattery`）、`providers.cpp:1882-1899`、`:1932-1940`
- 影响：当前把"一个 Main Item"压成"一个字段"，把所有 usage 塞进同一个 `bitOffset`，再在调用侧用 `reportId != 0` 决定要不要跳过首字节。三个假设只要有一个不成立就静默读错。
- 方向：
  1. `ParseDescriptor` 里按 `reportCount` 把每个 usage 展开成独立字段，`bitOffset = itemStart + i * reportSize`；`reportCount=0` 或 usage 数量不匹配时按 HID 规范取第一个 usage；
  2. `FindBattery` 直接把 `ReportField` 复制成 `BatteryField`，不再二次推导；
  3. 调用侧**无条件**跳过 `buf[0]`（`HidD_GetFeature` 的缓冲区首字节永远是 Report ID，无 ID 时为 0）；
  4. `NormalizeLevel(value, logicalMin, logicalMax)` 用 `(v-min)*100/(max-min)`，`max<=min` 时拒绝而不是回退到 100；
  5. `ExtractBits` 前置校验 `bitOffset>=0 && bitSize>0 && bitSize<=32 && bitOffset+bitSize <= payloadLen*8`，用 `uint32_t` 累加。
- 验证：本轮 `t2.cpp` 那五个用例可以直接固化成单测（0..1 / 0..10 / 0..100 / 电量在第 2 项 / 短帧），断言分别是 100、100、100、100、`nullopt`。

**（2）设备身份改成物理设备级** — 关闭 C3。

- 定位：`providers.cpp:1774`（索尼）、`:1385`（飞智）、`:1200`（Nordic）、`:1244`（迈从）、`:1944`（通用）、`main.cpp:70`
- 方向：key 优先级 `ContainerId → 序列号 → 接口根路径 → VID:PID+产品名`；`HidInfo` 增加 `containerId`（`SetupDiGetDeviceRegistryPropertyW` 的 `SPDRP_BASE_CONTAINERID`）与 `rootPath`（`StripSuffix(path, "&col")`，罗技分支已在用）。
- 验证：构造两组同 VID:PID、不同根路径的 `HidInfo`，断言产生两条 `Reading`；同一设备两个集合断言只产生一条。

**（3）休眠与缓存语义分离** — 关闭 C5、C6。

- 定位：`main.cpp:67-73`、`providers.cpp:2094-2105`、`:412-441`
- 方向：`Reading` 增加 `sampledAt`（真正读到值的时刻）与 `stale`；`Scan()` 合并时，若新记录是明确占位（`level<0 && status` 表示休眠）且旧记录有有效 `level`，则保留旧 `level/voltage/charging` 与旧 `sampledAt`，只把 `stale=true` 与 `misses` 加上；UI 时间文案改用 `sampledAt`，并显示"（缓存）"。
- 验证：喂"80% 有效 → 休眠占位"两条，断言第二条仍是 80% 且 `sampledAt` 不变；BLE 缓存推进 8 轮，断言 UI 年龄连续增长而不是归零。

### 5.2 第二优先：把探针从"一次性脚本"变成可信基础设施

- **修 `hidprobe.py` 三处**（N1、N9、P4/P5）：`xfer` 双句柄；`_read_timeout` 超时后 `CancelIoEx` + `GetOverlappedResult(..., TRUE)`（可直接搬 `probe_final.py:31-34`）；`SetupDiDestroyDeviceInfoList` 替掉 `CloseHandle(hdev)`；`SP_DEVICE_INTERFACE_DETAIL_DATA_W` 按 `need` 动态分配。
- **修 `caps.py`**（N2）：四个 `BOOLEAN` 改 `c_ubyte` + `assert sizeof == 72`。这个工具修好后是验证 C2/C8 修复的最直接手段。
- **脚本分级**：按"只读 / 会写设备 / 会杀进程"三档打标签，`featscan*`、`scan13`、`scanrid*`、`sony_enable/mode*`、`shot_panel`、`frost_check` 全部归入后两档；默认入口只暴露只读子命令。
- **统一入口**：`probe_cli.py enum|listen|desc|read|send`，参数校验集中；一次性脚本移入 `experiments/`，只把验证过的留 `tools/`。
- **回归样本**：每个协议存一组"请求帧 + 期望应答"的 hex fixture（迈从 V1/V2、飞智、Compx、索尼 USB/蓝牙各一），解析函数改成纯函数后做离线断言——这是唯一能在没有硬件时防止协议回归的办法。

### 5.3 第三优先：稳定性与工程门禁

- **C11**：退出路径改为"置取消标志 → 可等待句柄上 `WaitForSingleObject(INFINITE)`"；给 `HidD_GetFeature` 也加上 `CancelIoEx` 能力（改成 overlapped Feature），否则 1.5 s 这个数字永远只是赌运气。`CloseHandle` 不能当 join。
- **C10**：`EnsureSurface` 保存 `HGDIOBJ old = SelectObject(dc, dib)`，`DestroySurface` 先 `SelectObject(dc, old)` 再 `DeleteDC`，最后 `DeleteObject(dib)`。对照 `frost_check.py:117-120` 的顺序是可用的（那里先 `DeleteDC` 再 `DeleteObject`）。
- **C13**：`if (wp) { g_forceScan = true; g_scanManual = true; }`，普通刷新只置位不清位。
- **C14**：`AutostartSet` 返回 `bool`，失败不更新 `g_config.autostart` 并回滚开关；`ExePath` 用两次 `GetModuleFileNameW` 取长度。
- **门禁**：`build.bat` 的编译行加 `-Wall -Wextra`，把当前 warning 基线记下来（上一轮记录了 `ui.cpp` 的 `int/float` 转换与 `a` 遮蔽、`providers.cpp` 的 `n` 遮蔽），此后只允许减少不允许增加。

## 8. 结论

上一轮把主要风险点找得比较准：**C1/C2/C8 是同一条"没有按描述符正确解析"的根因**，本轮用真实代码喂构造报文，把这个根因的三个表现都复现了出来——这不是推测，是 `raw=0` / `level=1` / `raw=17` 三行实测输出。

本轮补完 50 个 Python 脚本后，探针侧的问题比上一轮判断的更集中：**公共库的异步 I/O 和 `xfer` 写路径是坏的（P1/N1），唯一的结构体级工具 `caps.py` 是错的（N2），另有 9 个脚本用了自己文档里明确禁止的单句柄方法（N3）**。也就是说，"用探针验证协议"这条路径目前还不具备可信度，而它恰恰是修 C1/C2/C8 时最需要的验证手段。

建议顺序：**先修 `hidprobe` + `caps.py`（半天）→ 用修好的 `caps.py` 拿真机描述符确认 C1/C2/C8 的触发面 → 再改 `ParseDescriptor`/`NormalizeLevel`（一天）→ 然后才是 C3/C5/C6 的身份与缓存模型**。反过来做，会在没有可信验证工具的情况下改协议解析，风险更高。
