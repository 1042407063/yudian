## 1. 描述符解析（P0 组）

### C1 通用 HID `reportId=0` 偏移错误

- **建议**：无条件跳过 `HidD_GetFeature` 缓冲区首字节。
- **改动**：`providers.cpp` 新增 `DecodeBatteryReport()`（供测试直接调用），`ScanGeneric` 改为调它。
- **方式**：`body = buf.data() + 1; bodyLen = size - 1;`，不再判 `reportId != 0`；`buf.size() < 2` 直接拒绝。
- **验证**：构造描述符 + 构造报文喂真实函数（`/tmp/verify/v.cpp`）。
- **结果**：`无ID, buf=[00 64]` → `level=100`（修复前 `level=0`）；`ID=5, buf=[05 64]` → 100。**通过**

### C2 未按 logical range 归一化

- **建议**：`NormalizeLevel(value, logicalMin, logicalMax)` 按区间线性映射。
- **改动**：`providers.cpp:NormalizeLevel`（签名从 2 参改为 3 参）。
- **方式**：`(v-min)*100/(max-min)` 四舍五入；`max<=min` 时若 `max==0` 按 0..100 兜底，否则拒绝；越界值拒绝；结果夹到 0..100。
- **验证**：0..1、0..255、10..20、0..100 越界共 5 个用例。
- **结果**：`0..1 满值 → 100%`（修复前 1%）、`0..255 → 100%`、`10..20 中点 → 50%`、`越界 200 → 拒绝`。**通过**

### C8 同一 Main Item 内多个子字段时读错位置

- **建议**：`ParseDescriptor` 按 `reportCount` 展开每个 usage 为独立字段。
- **改动**：`hid.cpp:ParseDescriptor` Main Item 分支。
- **方式**：仅当该 Main Item 含电量 usage 且 `reportCount>1` 时展开，`bitOffset = itemStart + k*reportSize`；展开数上限 256，累加用 `long long` 后夹到 `INT32_MAX/2`。
- **验证**：描述符 `usages=[X, BatteryStrength], count=2`，报文 `[00 11 64]`。
- **结果**：`raw=100`（修复前 `raw=17`）。**通过**

### C12 描述符整数边界 / 位提取 UB

- **建议**：位宽、偏移、长度全部前置校验；用无符号移位。
- **改动**：`providers.cpp:ExtractBits`、`hid.cpp` 偏移累加。
- **方式**：`payload==nullptr / payloadLen<=0 / bitOffset<0 / bitSize<=0 / bitSize>32 / bitOffset+bitSize > len*8` 全部返回 -1；移位改 `1u << k`。
- **验证**：`off=-8`、`size=40`、`off=24,size=16`、正常 `off=8`。
- **结果**：三个非法用例均返回 -1（修复前 `off=-8` 读到了缓冲区之前的字节）；正常用例返回 2。**通过**

## 2. 设备身份与缓存语义

### C3 同型号多设备被 VID:PID 合并

- **建议**：key 优先级 ContainerId → 序列号 → 接口根路径 → VID:PID。
- **改动**：`hid.h:HidInfo` 增 `containerId/serial`；`hid.cpp:EnumHidDevices` 用 `SPDRP_BASE_CONTAINERID`（MinGW 缺该常量，本地补 `0x24`）与 `HidD_GetSerialNumberString` 填充；`providers.cpp` 新增 `DeviceIdentity()`，索尼/飞智/迈从/Nordic/通用 HID 全部改用它。
- **方式**：索尼额外做两步分组——先按 ContainerId，再把"同 PID 且恰好一组 USB + 一组蓝牙"合并（保持 README 第 35 条"USB/BT 合成一条"不回归）。
- **验证**：纯函数断言 + 真实枚举（只读）。
- **结果**：同型号两台 → 键不同；同一台两个集合 → 键相同；真实枚举 **12 个接口 → 2 台设备**。**通过**
- **过程中发现**：`27C6:01E0` 的 ContainerId 是 `{00000000-0000-0000-ffff-ffffffffffff}`（Windows 的"无容器"哨兵值），已识别并回退，否则多台无容器设备会被并成一台。

### C5 BLE 缓存被标成"当前时间"

- **建议**：缓存记录带 `sampledAt`，超期标 stale，不伪造 `updated`。
- **改动**：`app.h:Reading` 增 `sampledAt`、`stale`；`providers.cpp:ScanBle` 缓存复用时报 `stale=true` 并保留采样时刻；`main.cpp:Reading::AgeText` 改用 `sampledAt`；`ui.cpp` 对 `stale` 行显示"上次 X 分钟前"。
- **验证**：`MergeReading` 纯函数用例。
- **结果**：缓存记录 `sampledAt` 保持 T1、`stale` 保持 true、`updated` 更新为 T2。**通过**

### C6 休眠占位覆盖最后一次有效读数

- **建议**：占位记录保留旧 `level/voltage/charging/sampledAt`，并标 stale。
- **改动**：`main.cpp:MonitorState::Scan` 抽出 `MergeReading()`（放 `providers.cpp`，`app.h` 声明）便于测试。
- **验证**：19 条断言（含 0% 这种"有效零值"边界、旧记录本就没值时不伪造）。
- **结果**：`80% → 休眠占位` 仍显示 80%、采样时刻不变、标记 stale、仍算在线（不播离场动画）。**通过 19/19**

## 6. 新发现（本轮未修）

### N17（P0）用户态拿不到 HID 报表描述符，通用 HID 兜底整条链路是死的

- **证据**：
  - `IOCTL_HID_GET_REPORT_DESCRIPTOR (0x000B0007)` 在 **全部 12 个接口**上返回 `ERROR_INVALID_FUNCTION`；
  - `IOCTL_HID_GET_COLLECTION_DESCRIPTOR (0x000B0193, HID_CTL_CODE(100))` 能成功，但返回内容以 ASCII `"HidP KDR"` 开头 —— 是内部结构，不是描述符；
  - 因此 `LoadDescriptor()` 在改动前后都是 0/12 成功，`ScanGeneric()` 永远不会产生读数。
  - 直接后果：**C1/C2/C8/C12 的修复目前没有运行时效果**——它们修的是"拿到描述符之后"的逻辑。
- **已做的处置**：`LoadDescriptor` 现在会识别 `"HidP KDR"` 并拒绝，同时校验解析结果里必须有合法 `bitSize`，避免把内部结构当成描述符解析出"全零字段"（那是比失败更糟的状态）。两个控制码都会尝试，老系统不受影响。
- **建议的修法**：改用 `HidP_GetValueCaps`（`caps.py` 已证明可用、数值正确）合成 `ReportField`：按 report type 枚举 Value Caps，用 `BitSize × ReportCount` 在同 reportId 内累加出 `bitOffset`（HidP 按 DataIndex 顺序返回），再用 `HidP_GetUsageValue` 直接取值——这样 C1/C2/C8/C12 全部消失，不再需要解析原始描述符。
- **为什么没做**：本机没有"按标准 HID 上报电量的通用设备"，改了无法验证；而偏移累加是该方案唯一有风险的环节，盲改等于换一个未经验证的实现。

### N18（低）`--list` 在鼠标休眠时报告 0 台设备

- **证据**：新产物与备份里的旧产物在同一时刻都是 `devices=0`，而紧随其后的诊断能读到 20%。属既有行为，不是本轮回归。
- **影响**：把 `--list` 当回归基线时，会误判成"功能坏了"。

# 第四轮：C9 回退、毛玻璃调整、项目清理

## 1. C9 增加回退（严格优先，整窗兜底）

**问题**：上一轮把迈从 V2 的应答改成"校验不过就丢"，一旦真机固件不按文档算 XOR，
原本能读的 A5 V3 会变成"读不到电量"——这是全部改动里唯一可能让功能变差的点。

**设计**：把"一帧的判断"和"整个等待窗口的裁决"分开。

| 层 | 行为 |
|---|---|
| `MchoseV2Parse(buf, n, out, requireChecksum=true)` | 严格：帧头 / 命令 / 长度 / 取值范围 / XOR 全过 |
| `MchoseV2Parse(..., false)` | 回退：同样的检查但跳过 XOR（等于改动前的旧行为） |
| `MchoseV2Offer()` | 一帧一帧喂，严格通过就立刻返回；否则把第一帧"仅回退可用"的记下来 |
| `MchoseV2Resolve()` | 窗口结束：有严格帧用严格帧，没有才用回退帧，都没有才算失败 |

**可见性**：`VendorBattery` 增加 `checksumVerified`；回退时 `ScanMchose` 把
`detail` 写成"应答校验未通过，已回退到旧解析（固件算法可能与协议文档不一致）"，
不静默降级。V1 的求和校验通过时也标 `checksumVerified = true`，避免误报。

**取舍**：整窗都没有合法帧时，仍然采信回退帧。这是有意的——宁可显示一个可能
不准的读数，也不要让设备"凭空消失"；不确定性通过 detail 文案交给用户判断。

**验证**（`/tmp/verify/v14.cpp`，16 条断言，全部通过）：

```text
好帧 -> 立即返回 true；resolve 取 64；标记已校验
坏帧 -> 不提前结束；resolve 仍给出 64；标记未校验
坏帧先到、好帧后到 -> 最终采用 88（不是 21），且标记已校验
只有坏帧 -> 取第一帧回退值 21，未校验
命令不符 / 心跳帧 -> 两种模式都拒绝；无候选 -> resolve false
恰好缺校验字节 -> 严格拒、回退也拒（长度检查不会被回退绕过）
```

# 提示窗外多出一个方框（DWM 圆角描边）

## 现象

低电量提示卡外面浮着一个硬边方框，白底上尤其明显。用户原话：「外面有一个方框，看着好膈应」。

## 定位

先把截图逐像素读出来量，再在没有干扰的环境里复现：

- 白底全屏背景上抓提示窗，窗口**最外一圈 3px 是灰线** `(165,165,165)`，而该处本应完全透明；
- 四角更浅（224），说明它沿圆角走——是**窗口外框**，不是卡片描边（卡片描边在 54px 里面）；
- 把 `ApplyPanelCorners()` 里设置 `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND` 的那两行临时去掉，
  重新编译再抓：四边全部变成纯白 255。**根因确认。**

## 根因

`DwmSetWindowAttribute(hwnd, 33, DWMWCP_ROUND)` 会让 DWM 沿**整个窗口矩形**补一圈 1px 描边。

提示窗改成分层窗口后，窗口尺寸 = 卡片 + 四周 36 DIP 的阴影余量，比卡片大一圈。
于是 DWM 的描边画在了**阴影余量的外沿**，离卡片 36 DIP，看起来就是一个孤零零的方框。

> 这是我上一轮「提示窗统一到面板玻璃材质」时引入的回归：改成分层窗口后，窗口从「等于卡片」
> 变成「卡片 + 阴影余量」，而 `ApplyPanelCorners` 的圆角请求没跟着调整。
> 描边颜色受 `DWMWA_USE_IMMERSIVE_DARK_MODE` 影响：浅色下是灰 165，深色下是一圈亮线。

## 修复

`ui.cpp` · `ApplyPanelCorners`：不再请求 DWM 圆角。

```cpp
// 圆角只靠卡片自己画（分层窗口逐像素 alpha），不要再设 DWMWA_WINDOW_CORNER_PREFERENCE。
// 一旦让 DWM 去圆角，它会沿整个窗口矩形补一圈 1px 描边，而窗口比卡片大一圈阴影余量，
// 于是卡片外面凭空多出一个方框。
if (build < 22000) {          // Win10 及更早：仍然用窗口区域兜底
    ...SetWindowRgn(...)
}
```

深色标记（`DWMWA_USE_IMMERSIVE_DARK_MODE`）保留——它只影响 DWM 画的边框/阴影颜色，没有边框时无副作用。

## 验证

| 项 | 方法 | 结果 |
|---|---|---|
| 浅色提示窗四边 | 白底抓屏，逐像素比较 255 | 上/左/下三边**非白 0 个** |
| 深色提示窗四边 | 临时把 `config.ini` 的 `theme` 改为 `dark`，抓完还原 | 三边**非白 0 个**，卡片中心 `(113,115,118)` |
| 面板 | 同一份抓屏脚本 | 三边非白 0 个（面板本来就没调用这个函数，未受影响） |
| 条纹背景目视 | 全屏彩色横条背景抓屏 | 无方框，条纹透过玻璃，圆角与阴影正常 |

| 退出 | 提示窗开着时 `WM_CLOSE` | 0.08s 干净退出 |

# 毛玻璃背后的画面不跟着桌面变

## 现象

面板开着的时候，背后的窗口关掉了，玻璃里还留着它的影子——像卡住了一样。

## 原因

毛玻璃底图只在**面板弹出那一刻**抓一次（`CaptureBackdrop`），之后一直复用。画面是"冻结的照片"，
桌面一变就成了"已经不存在的东西"。

## 为什么不能简单地定时重抓

重抓时必须把面板自己排除出画面，否则会拍到自己，玻璃里嵌着一张自己的影子（递归）。

最直觉的做法是"抓之前把窗口藏起来、抓完再显示"，但那样屏幕会闪一帧；每 0.7 秒闪一次，
比底图过期更难受。

## 修复

用 `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`：**只把自己从画面里摘掉，
屏幕上的显示不受影响**。实测设置后紧接着 BitBlt 就已生效，不需要隐藏窗口、也不会闪。

| 位置 | 改动 |
|---|---|
| `CaptureExclusion`（新增） | RAII：构造时设置排除、析构时还原，任何提前返回都不会漏掉 |
| `CaptureBackdrop` | 增加 `exclude` 参数；返回 `bool`，排除失败时让调用方放弃本次抓屏 |
| `RefreshPanelBackdrop`（新增） | 重拍 + 决定要不要重画 |
| 面板 | 显示时 `SetTimer(4, 700ms)`，隐藏时 `KillTimer`；卡片动画中 / 拖动中跳过 |

### 两个关键细节

**1. 必须 `DwmFlush()`。** 不调的话，每十几次会有一次仍抓到自己的画面（实测跳变上万像素）——
玻璃层会偶发地闪一下自己的影子。加上之后稳定。

**2. 不能只比哈希。** 桌面上的光标闪烁会改一两个像素，被模糊一糊根本看不见，却会让面板每秒重画好几次。
改成逐像素比、允许 24 个像素以内的差异（约 0.1%），于是：

- 静置 → 只抓屏、不重画
- 关掉一个窗口 → 上万像素变化 → 重画一次

## 顺带优化

| 项 | 改前 | 改后 |
|---|---|---|
| 降采样 | GDI+ 高质量双三次 | 手写 4×4 盒式平均（**4~6ms → 0.2ms**） |
| 抓屏开销 | 每次约 13ms | 每次约 6ms |

> 这块图后面还要被模糊掉，双三次的精度没有意义。

## 验证

| 项 | 方法 | 结果 |
|---|---|---|
| 底图会跟着变 | 面板开在纯黑全屏窗口上，然后销毁该窗口 | 玻璃亮度 **158.9 → 233.9**（0.7s 内） |
| 不会拍到自己 | 条纹背景抓屏目视 | 无嵌套卡片、无重影 |
| CPU（面板开） | `GetProcessTimes` 6 秒取样 | 4.43%（400ms）→ **2.08%（700ms）** |
| CPU（面板关） | 同上 | **0.00%** |
| 构建 / 警告 | 全警告编译 | 28 条，与基线持平 |
| 离屏渲染 / 退出 | `--shot`、`--shot-toast`、提示窗开着 `WM_CLOSE` | 全部正常，退出 0.09s |

> 代价说明：面板**打开期间**多花约 2% 单核（每次抓屏 ~6ms）。面板一收起就归零，
> 常驻期间的资源占用不受影响。老系统若不支持 `WDA_EXCLUDEFROMCAPTURE`，定时器会自己停掉，
> 退回"只抓一次"的旧行为——不会拍到自己。

# 取消毛玻璃：卡片改回不透明

## 决定

上一轮做的「底图每 0.7 秒重拍」虽然能让玻璃跟上桌面，但用起来是割裂的：

- 拖动面板时玻璃**完全停住**（拖动中刻意跳过了刷新），松手才补上；
- 不拖动时也有最多 0.7 秒的滞后，眼睛能感觉到"这块画面跟不上"；
- 面板打开期间多花约 2% 单核。

试过几轮都没法做到真正的实时——分层窗口拿不到 DWM 的实时模糊，只能靠抓屏，
而抓屏必然有延迟、必须排除自己、还不能太频繁。**成本与收益不匹配，整块去掉。**

## 改了什么

| 项 | 处理 |
|---|---|
| `CaptureBackdrop` / `BlurArgb` / `BlurRadiusFor` / `CaptureExclusion` / `BackdropTrack` | 全部删除（约 240 行） |
| `g_backdrop` / `g_toastBackdrop` / 定时器 4 | 删除 |
| 面板卡片 | 回到不透明的垂直线性渐变（`bg → bg2`） |
| 提示窗卡片 | 回到不透明纯色（`bg` / 深色 `tile`） |
| `Colors::glass` | 删除（已无使用者） |

保留的是真正被验证有效的那部分：分层窗口、两层高斯阴影、16px 圆角、动画、提示窗与面板统一的材质。

## 结果

| 指标 | 改前 | 改后 |
|---|---|---|
| 面板打开时 CPU | 2.08% | **0.00%** |
| 拖动时的玻璃 | 停住不动 | 不存在这个问题 |
| 界面是否受桌面影响 | 会（滞后/过期） | **完全不会** |
| exe 体积 | 613,376 B | 606,720 B |
| 编译警告 | 28 | **28** |

代码净减约 280 行。卡片依然靠 1px 描边 + 柔和阴影和背景分开，白底上也不会糊成一片。

## 验证

- 条纹背景抓屏：卡片内**看不到条纹**（不透明），圆角/阴影/文字正常；
- 提示窗同理；`--shot`、`--shot-toast` 离屏渲染正常；
- 面板打开/关闭 CPU 都是 0.00%；提示窗开着时退出 0.07s；
- 全警告编译 28 条，与基线持平。

# 卡片配色 + 右键菜单圆角 + Win10/11 兼容性体检

## 1. 卡片不再是纯白

| | 改前 | 改后 |
|---|---|---|
| 顶部 | `#FFFFFF` | `#F7F8FA`（偏冷的浅灰） |
| 底部 | `#FBFBFD` | `#F1F2F6` |
| 渐变幅度 | 约 1% | 约 2% |

纯白贴在白色窗口上会糊成一张纸；偏冷的浅灰才像"一块有厚度的材质"。
文字仍是 `#141416`，对比度没有损失。

## 2. 右键菜单圆角

**现象**：托盘右键菜单是方角 + 1px 硬边，和面板/提示卡的圆角完全两个年代。

**根因**：程序没有应用清单。没有 `supportedOS` 声明时，系统按兼容模式画菜单，
拿到的是老式外观。

**做法**（两条一起）：

1. 加 `src/app.manifest` 并在 `app.rc` 里以 `1 24` 编入资源——声明支持 Win10/11 + 现代通用控件。
2. 菜单窗口是在 `TrackPopupMenu` 内部创建的，拿不到句柄。于是弹出前挂一个 10ms 定时器：
   `TrackPopupMenu` 自己会跑消息循环，定时器照样能进来，抓到类名 `#32768` 的窗口后
   给它补 `DWMWA_WINDOW_CORNER_PREFERENCE = ROUND`，返回后摘掉定时器。

**实测**：菜单左上角的轮廓从"第 6 行就到边"变成"第 11 行才收进"，放大 6 倍可以看到平滑圆弧 + 柔和阴影。

## 3. Win10 / Win11 兼容性体检

用户要求两个系统都要能用，逐项核对：

| 项 | 结论 |
|---|---|
| 最低系统 | **Windows 10 1607**（`SetProcessDpiAwarenessContext`、`GetDpiForSystem` 从 1607 才有） |
| Win11 专属：菜单圆角 | 已用 `WindowsBuild() < 22000` 提前挡掉，Win10 上不调用 |
| Win11 专属：提示窗圆角 | 有 Win10 退路：`SetWindowRgn` 区域裁圆角 |
| 深色边框 `DWMWA_USE_IMMERSIVE_DARK_MODE` | 20 失败自动退 19，再失败就忽略，三层兜底 |
| 清单里的 supportedOS | **原来写了 Win7/8/8.1，是假的**（那些系统上程序根本起不来），已删除，只留 Win10/11 |
| DPI | 加清单后实测仍为 `dpi=144 awareness=PerMonitorAware` |

> Win10 上右键菜单保持系统原生的方角——那个系统里所有菜单都是方角，硬掰成圆角反而不像它。

## 验证

- 菜单：圆角 + 阴影，勾选/子菜单/键盘操作全部保留（还是系统菜单）；
- 面板：冷调浅灰卡片，条纹/白底背景都不再透出；
- 构建 28 条警告与基线持平；`--shot`、`--shot-toast`、`--list` 正常；提示窗开着退出 0.07s；
- 面板开/关 CPU 均 0.00%。

# 点通知的 × 却弹出面板（坐标空间用错）

## 现象

低电量通知右上角点 ×，通知消失了，但**面板跟着弹出来**。

## 定位

`ToastProc` 的两个鼠标分支里，判断写的是：

```cpp
POINT pt{GET_X_LPARAM(lp), GET_Y_LPARAM(lp)};
bool onClose = PtInRect(&g_toastCloseRect, pt) != 0;
UiHideToast();
if (!onClose) PostMessageW(g_mainWnd, WM_APP + 5, 0, 0);   // WM_APP+5 → UiTogglePanel()
```

逻辑没错，错在**两套坐标**：

| | 坐标系 | 关闭热区实际位置（150% 缩放） |
|---|---|---|
| `g_toastCloseRect`（`DrawToastContent` 里记的） | 卡片坐标 | `x 530..562, y 14..46` |
| `pt`（鼠标消息给的） | 窗口客户区坐标 | 真正的 × 在 `x 600, y 84` |

通知改成分层窗口后，窗口 = 卡片 + 四周 36 DIP 的阴影余量，`ComposeToast` 里有一句
`TranslateTransform(m, m + slide)` 才画卡片。热区记的是平移**之前**的坐标，鼠标消息
给的却是平移**之后**的，两者差 54px。于是点可见的 × 永远落在热区之外 →
`onClose=false` → 顺带把面板叫了出来。

同一处偏差还让悬停高亮画在了卡片左上方的阴影里，从来没有真正落在 × 上。

> 这是提示窗改分层窗口（统一玻璃材质那轮）留下的回归：窗口从「等于卡片」变成
> 「卡片 + 阴影余量」，绘制加了平移，鼠标分支没跟着改。

## 修复（`app/src/ui.cpp`）

新增一处换算，把鼠标点翻回卡片坐标，与绘制用的变换**完全对应**：

```cpp
POINT ToastCardPoint(POINT pt) {
    const int m = ShadowPx();
    pt.x -= m;
    pt.y -= m + g_toastSlide;     // 入场动画期间卡片还在滑，一起算进去
    return pt;
}
```

`WM_MOUSEMOVE` 与 `WM_LBUTTONUP` 都先过这一层。同时给「叫面板」加一道护栏：

```cpp
const bool inCard = pt.x >= 0 && pt.y >= 0 && pt.x < ToastW() && pt.y < ToastH();
UiHideToast();
if (!onClose && inCard) PostMessageW(g_mainWnd, WM_APP + 5, 0, 0);
```

阴影那圈半透明像素也能收到点击，落在卡片外时只关通知、不弹面板。

## 验证（真实鼠标点击，`SendInput`）

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 点 × | 通知关、**面板弹出** | 通知关、面板不弹 |
| 点卡片正文 | 通知关、面板弹出 | 不变（原功能保留） |
| 点卡片外的阴影 | — | 只关通知 |
| 悬停 × | 高亮画在阴影里 | 差异为半径 ≈17px 的圆盘、居中于 × |
| 6 秒后自动消失 | 不弹面板 | 不弹面板（未受影响） |

回归：构建通过、警告 **28 条**（与基线持平）、`--shot` / `--shot-toast` / `--list` 正常
（读到 1 台设备 20%）、提示窗开着时退出 **0.05s**。

# 雷柏 M200 系列：列为「硬件不支持读数」

## 需求

M200 / M200G / M200G Plus 在面板里**完全看不到**。用户要求：读不到也要出现，好知道程序认出了它。

## 能不能读：三条路都走完了

| 路径 | 做法 | 结果 |
|---|---|---|
| 标准 HID 电量字段 | 用 `HidP_GetValueCaps` 扫全部接口，找 `0x06/0x20` | **不存在** |
| 雷柏私有通道 | `0xFF00:0x000E`、report `0xBA`，按公开协议发 `a3` 握手 / `a4` 读寄存器 / `aa` 读电量；`SetOutputReport` 与 `WriteFile` 两种发送、五种连接字节 | **全程无应答**（连文档里可读的性能寄存器也不回） |
| 唯一的 8 字节特性报告 | `0001/0000` 上 report `0x05` | 恒为 `04 55 91 01 00 00 00 00`；鼠标持续活动 54 秒**一个字节都没变** → 是固定信息，不是电量 |

顺带确认：鼠标/键盘集合在 Windows 上只允许 `access=0` 打开，读不了输入报告——Linux 上“被动收 13 字节报文”那条路在 Windows 不存在。

**结论：2.4G 模式下没有可读电量。** 不硬凑那 85%。

## 实现（`app/src/providers.cpp`）

新增 `ScanRapoo` / `ClaimsRapoo`，插在飞智之后、通用兜底之前：

- 按 `DeviceIdentity`（ContainerId）把接收器的多个集合归成一台；
- **只列鼠标**（有 `0001/0002` 集合），雷柏键盘不占行；
- `level = -1`、`status = 硬件不支持读数`、`outcome = Unsupported`、`detail` 说明原因；
- 认领该设备的所有接口，通用兜底不会再碰它。

与罗技 C542 那一代接收器同一类处理：**能识别、明确标注读不到**，而不是假装设备不存在。

## 验证

| 项 | 结果 |
|---|---|
| `--list` | `devices=2`，其中 Rapoo 一行：`-- / 硬件不支持读数 / rapoo`，汇总「不支持 1」 |
| 重复扫描两次 | 每次都是 **1 行**，不重复 |
| 面板渲染 | 截图确认：名字、`2.4G 接收器 · 雷柏 · 硬件不支持读数`、空电量图标、`--` |
| 低电量提醒 | `level < 0` 被跳过，不会误弹卡片 |
| 构建 / 警告 | 通过，**28 条**与基线持平，626,176 字节 |
| 退出 | 提示窗开着时 0.08s 干净退出 |

## 顺手纠正的文档

支持范围里原来写着「其它按 HID 规范上报电量的蓝牙键鼠 … 已实现」——这条兜底依赖报表描述符，而 Windows 用户态拿不到，实际不产生读数。已改为「**暂不可用**」并注明原因，不再当未兑现的承诺。

# G304「新电池 90% / 耗尽仍显示 20%」排查

## 先分清两层

用户怀疑「满电基准电压过高 / 电压→百分比公式有误 / 采样不准」。逐条核对后，**前两条不存在**，
第三条只对了一半。

### 90% 是鼠标报的，不是我们算的

直接读 HID++ 原始应答（G304，通道 1，特性 `0x1000`）：

```
请求 11 01 05 0f ...
应答 11 01 05 0f 5a 32 00 ...
             ^^ 参数[0] = 0x5A = 90
```

代码 `HppLink::Battery()` 只做两件事：`raw > 100` 时掩码 `& 0x7F`，否则原样用。
90 没触发掩码。**程序里没有任何「基准电压」或「电压→百分比」的换算**——G304 的 `0x1001`
（电压特性）根本不支持（`GetFeatureIndex` 返回 -1），想换算也没有数据源。

公开资料也一致：G304 的百分比是固件按放电曲线估的，新碱性电池常见 90%，红灯慢闪约
15~20%，且**常在 20% 附近突然断电**。这两个数字是设备特性，不是本程序的误差。

### 20% 是我们留住的

`MergeReading()` 原本这样写：设备这一轮没应答（`level = -1`）时，无条件沿用上一次的
百分比，并把 `sampledAt` 一起保留。电池耗尽后鼠标不再应答，占位记录每 5 分钟来一次，
于是**最后那个 20% 被无限期续命**，界面上看起来就像电量卡住了。

更糟的是 `CheckLowBattery()` 只判断 `level >= 0`，会拿这个缓存值反复触发低电量提醒。

## 修复

| 位置 | 改动 |
|---|---|
| `MergeReading()` | 旧值沿用加 **15 分钟上限**；超时后 `level` 保持 -1、状态改「长时间无响应」，最后读数与时长写进 detail（面板不显示 detail，只进诊断） |
| `CheckLowBattery()` | `stale` 的记录不参与提醒——真低电会在设备应答的那一轮正常触发 |

为什么是 15 分钟：扫描间隔 5 分钟，G304 对 HID++ 请求会应答（实测空闲数分钟后 `--list`
仍能读到 90%）。连续 15 分钟不应答，基本就是关掉了、没电了或超出范围。

## 验证

| 项 | 方法 | 结果 |
|---|---|---|
| 沿用/丢弃边界 | `merge_test.cpp` 16 条断言 | 3 分钟沿用 20%；2 小时→`level=-1`、状态「长时间无响应」、detail 含「20% / 120 分钟」；15 分钟整仍沿用、超 1 秒即丢弃；新读数 88% 正常刷新；无旧记录/旧记录无时间戳不误伤 |
| 真实设备 | `--list` | 仍为 `90% · 放电中`（说明读数没被改动） |
| 构建 / 警告 | `build.bat` + 全警告编译 | 通过，626,688 B，**28 条**与基线持平 |

## 建议

- **不要**给罗技这条链路加「电压→百分比」的再映射：拿不到电压，且会与 G HUB 的数字打架。
- 判断换电池请看设备自己的低电提示（G304 红灯慢闪≈15~20%），别把 20% 理解成「还有两成续航」。
- 若希望界面更明确，可以给罗技行加一个「≈」或「设备估算」标记——这是显示层决定，等确认。
